# ARGO 工程哲学：确定性交付公式的工程化

ARGO 的工程方法不是单纯把 AI Agent 串成一条自动化流水线，而是围绕“AI 确定性交付”这个目标，把需求澄清、领域建模、架构契约、测试门禁、任务颗粒度和人类审核组织成一个闭环系统。

## ARGO 这个名字

ARGO 取意于希腊神话中的 **阿尔戈号（Argo）**。阿尔戈号不是一件单人武器，而是一艘承载多位英雄共同远航的船。它的意义不在于某个英雄单点爆发，而在于把船员、航线、目标、纪律、协作和风险应对组织成一次可抵达目的地的远征。

这与 ARGO 的工程哲学高度契合。AI Coding 中的大模型像强大的船员，具备推理、生成、搜索和修复能力，但它不能替代航线、船体结构、边界纪律和领航判断。ARGO 要构建的正是这艘“工程之船”：`BusinessPartner` 帮助确定目的地，意图图谱和实现架构契约定义航道，`Orchestrator` 负责调度船员，测试和验收门禁提供风浪中的校准，人类伙伴则在关键岔路口承担目标确认与价值判断。

因此，ARGO 不是“让 AI 自由发挥”的工具，而是一套让 AI 在清晰航道中协同交付的工程系统。它承认远征本身存在不确定性，所以用协议、边界、任务颗粒度和人类门禁把不确定性收束到可管理范围内。

它背后的核心公式是：

$$Total Certainty = C \times \frac{(P \cdot \mathbf{B}) \times E}{G}$$

其中：

- **C：Clarity（目标清晰度）**
- **P：Protocol（协议规范）**
- **B：Binding Power（边界约束力）**
- **E：Efficacy（模型能效）**
- **G：Granularity（任务颗粒度）**

ARGO 的工程哲学可以概括为一句话：**不要幻想模型天然稳定，而要通过工程系统提高目标清晰度、协议规范、边界约束和模型能效，同时降低单次任务颗粒度。**

## 从“让 AI 写代码”到“让 AI 在轨道上交付”

传统 AI Coding 的不确定性，往往来自几个叠加因素：

- 需求没有被充分澄清，AI 只能在模糊语义中猜测目标。
- 架构和领域知识停留在对话里，没有成为稳定事实源。
- 测试太晚出现，直到编码后才发现意图偏差。
- 任务过大，单次上下文里同时混入业务、架构、实现和调试问题。
- 缺少明确门禁，AI 的错误输出会持续污染后续上下文。

ARGO 的答案不是“换一个更强模型”，而是承认模型能力只是公式里的 **E**。模型能效当然重要，但确定性交付不能只押注在模型原生能力上。真正可工程化的路径，是系统性改造 **C、P、B、G**，让 AI 的推理和生成活动始终被清晰目标、稳定协议、强约束和小颗粒任务牵引。

## C：用业务拷问提高目标清晰度

公式中的 **C** 是目标清晰度。ARGO 认为，确定性交付的第一步不是进入开发，而是先把“想做什么”从模糊愿望坍缩成清晰、可验证、可拆解的业务目标。

因此，新需求开发不是从 `Orchestrator` 或编码开始，而是先通过 `BusinessPartner` Agent 或 `/business-partner` Skill 提交需求。`business-partner` 会围绕 SMART 和 MECE 原则做结构化拷问：

- 问题是否具体、可衡量、可判断完成。
- 业务方案是否被拆成互斥且穷尽的决策树。
- 每个分支的依赖、风险、控制点和观测点是否闭合。
- 验收测试用例是否站在验收方视角定义清楚。

这一步的本质，是提高 **C**：让 AI 后续面对的不是一团自然语言，而是经过人类和 AI 共同压缩、校正、验证过的目标坐标。

## P：用架构事实源和测试契约定义合法轨道

公式中的 **P** 是协议规范。ARGO 把协议规范拆成几类稳定资产：

- `design/KG/SystemArchitecture.json`：意图架构和领域事实的结构化载体。
- `OVERALL_ARCHITECTURE.md` 与局部 `ARCHITECTURE.md`：实现架构契约。
- `IntentToImplementationHandoff.json`：意图设计向实现设计的交接契约。
- `ImplementationToCodingHandoff.json`：实现设计向编码修复的交接契约。
- 显性验收 testcase、系统测试、集成测试和测试入口。

这些资产共同定义了 AI 可以走的“合法路径”。它们不是事后文档，而是后续 Agent 执行任务时必须读取、遵循、更新或验收的协议层。

ARGO 在这里引入了 SDD、TDD 和 DDD 的组合：

- **SDD** 让规格和架构不再只是自然语言，而是可以被 schema、图谱和 validator 检查的结构化对象。
- **TDD** 被前移到意图设计和实现设计阶段，先定义验收边界和测试入口，再进入编码。
- **DDD** 让领域概念、业务能力、约束、关系和边界沉淀为长期上下文，而不是散落在一次性对话中。

也就是说，ARGO 的 **P** 不是一份静态文档，而是一组可传递、可校验、可回归的工程协议。

## B：用门禁和闭环增强边界约束力

公式中的 **B** 是边界约束力。它决定 AI 偏航时，系统能不能及时“判、拦、纠”。

ARGO 的边界约束主要来自强阶段和强门禁：

- `IntentionDesign` 只负责意图规格、领域关系、验收 testcase，不直接改代码。
- `ImplementationDesign` 只负责实现架构、测试入口、实现交接，不改意图图谱。
- `CodingAndReparing` 只负责根据实现交接和失败记录修复真实实现，不修改冻结测试和架构契约。
- 人类伙伴必须审核意图验收用例和实现验收用例。
- 代码完成后还要经过代码实现验收和实现交付验收。

这套机制把 AI 的自由度限制在当前阶段允许的边界内。一旦发现问题，系统会根据问题归属回到正确阶段：

- 意图架构问题回到新需求开发前置流程。
- 实现架构问题先由 `ImplementationDesign` 调整架构和测试入口，再进入编码。
- 纯代码 BUG 才直接进入 `CodingAndReparing`。

这就是 **B** 的工程化：不是靠提示词里一句“不要跑偏”，而是把跑偏变成可发现、可阻断、可回流的流程。

## G：用 task-tidy 降低任务颗粒度

公式中的 **G** 是任务颗粒度，位于分母。单次任务越大，随机干扰越多，AI 越容易在一个上下文里同时处理业务、架构、实现、测试和调试，最终导致判断混乱。

ARGO 使用 `task-tidy` 把分析结果整理到 `design/tasks/`，并要求每个任务独立成文，包含：

- 任务背景。
- 相关 PRD 或业务来源。
- 执行内容。
- 验收标准。

任务切分同时遵循两个方向：

- **横向切分**：按功能模块或业务流程切出相互正交的任务。
- **纵向切分**：按依赖顺序组织任务，保证前置条件先被满足。

但 ARGO 不鼓励多个任务并发交给 Agent 执行。即使任务可以横向区分，也建议由人类伙伴按顺序逐个启动新会话提交给 `Orchestrator`。这样做是为了让每次 AI 执行面对更小、更纯净、更可验证的上下文。

降低 **G** 的目标不是“把流程变慢”，而是减少单次跳跃的不确定性，让每一次迭代都足够小、足够清楚、足够可验收。

## E：通过上下文组织释放模型能效

公式中的 **E** 是模型能效。ARGO 不直接改变模型本身，但它通过上下文工程让模型更容易发挥能力。

干净的架构、明确的事实源、分阶段交接和聚焦任务，会显著提高模型的有效推理能力：

- Agent 不需要在巨大代码库中盲目搜索目标。
- Agent 能从意图图谱和架构契约中获得稳定上下文。
- Agent 知道当前阶段能做什么、不能做什么。
- Agent 能用测试入口和失败记录判断修复是否完成。

因此，ARGO 强调架构 clean 程度与 AI Coding 质量密切相关。浅模块、泄漏的接口、错误的 seam、穿透实现的测试，都会降低模型的有效能效。`/improve-codebase-architecture` 的价值，正是通过识别 shallow module、职责泄漏、依赖方向问题和测试面失焦，提升 AI 对代码库的可导航性。

在这个意义上，架构优化不是“人类审美”，而是提高 **E**、降低 **G**、增强 **P** 和 **B** 的基础工程动作。

## 人类不是旁观者，而是确定性的校准器

ARGO 并不追求全自动。它明确把人类伙伴放在关键节点上：

- 通过 `business-partner` 提交和校准需求。
- 通过 `task-tidy` 确认任务切分。
- 按顺序启动新会话并提交任务。
- 审核意图验收用例和实现验收用例。
- 在测试环境、外部依赖、权限、设备等问题上提供帮助。
- 在架构优化中选择值得深挖的候选方向。

这些人类参与点不是自动化的失败，而是确定性交付的组成部分。AI 擅长生成、推理、搜索和执行；人类负责价值判断、边界确认、优先级选择和组织语境校准。

ARGO 的人机协作原则是：**让 AI 做可协议化、可验证、可回归的执行；让人类守住目标、边界和价值判断。**

## ARGO 的核心工程信念

ARGO 的工程哲学可以总结为以下几条信念：

1. **确定性来自系统，不来自单次聪明回答。**  
   好的 AI 工程不是让模型“这次答对”，而是让它在多轮、多任务、多角色中持续不偏航。

2. **需求清晰度是第一生产力。**  
   模糊需求进入编码阶段，只会把不确定性放大成架构返工和测试失败。

3. **架构和测试必须成为事实资产。**  
   它们不是交付后的说明书，而是 AI 执行过程中的导航图和护栏。

4. **测试越早出现，偏差越早暴露。**  
   验收 testcase 从意图设计阶段开始出现，才能防止错误理解一路传递到代码。

5. **任务越小，确定性越高。**  
   小任务不是低效率，而是降低随机性、提高可验证性的采样策略。

6. **干净架构是 AI Coding 的基础设施。**  
   深模块、稳定接口、真实 seam 和 interface 级测试，会让 AI 更容易理解和修改系统。

7. **人类门禁是价值判断，不是流程阻塞。**  
   人类审核关键验收边界，是为了避免 AI 用错误测试固化错误理解。

## 结语

如果把大模型看作引擎，ARGO 关注的不是只给引擎加油，而是修轨道、设护栏、定目的地、缩短采样步长，并在关键岔路口安排人类校准。

这正是公式的工程含义：

$$Total Certainty = C \times \frac{(P \cdot \mathbf{B}) \times E}{G}$$

提高目标清晰度，构建协议规范，增强边界约束，释放模型能效，降低任务颗粒度。ARGO 的整套工程方法，就是把这个公式落实到 AI Coding 的日常交付流程中。
