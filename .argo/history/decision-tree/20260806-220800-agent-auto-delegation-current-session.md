# ARGO Large-Task Automatic Subagent Delegation Decision Tree

## Problem Definition

When BusinessPartner, IntentionDesign, ImplementationDesign, or CodingAndReparing encounters a large task, multiple independent hypotheses, broad evidence collection, or independent authorized change sets, the stage-owning Agent must automatically delegate bounded subwork so that the parent context contains only decision framing, constraints, structured evidence summaries, integration decisions, and final acceptance. Delegation must not weaken stage ownership, architecture semantics, write authorization, human approval, handoff validation, or delivery gates.

Because ARGO currently has no reliable token/context-window telemetry, phase-one success is measured through observable behavior proxies rather than an invented context-reduction percentage.

## Horizontal Architecture Concerns

1. **Delegation Governance** — common trigger, depth, concurrency, retry, return-contract, and accountability rules.
2. **Hypothesis and Evidence Governance** — proof and falsification plans, four evidence channels, authority precedence, and verdict semantics.
3. **Intent Architecture Delegation** — parallel read and proposal work with one Viewpoint-governed canonical graph writer.
4. **Implementation Architecture Delegation** — local stable-element parallelism with one owner for root and shared contracts.
5. **Coding and Repair Delegation** — dependency-DAG frontier execution with approved disjoint write sets and global verification.
6. **Cross-Stage Orchestration** — Orchestrator retains stage routing, handoff, approval, commit, audit, and completion gates.

These concerns are orthogonal because each owns a distinct decision boundary: common policy, epistemic proof, intent state, implementation design, executable code, or cross-stage workflow. They may evolve in parallel only while their declared interfaces and final responsibility boundaries remain stable.

## Vertical Dependency Chain

1. Define the stage-owned task and preserve its final accountable Agent.
2. Evaluate the five hard triggers and four prohibition conditions.
3. Define hypotheses, proof and falsification conditions, required evidence channels, authority precedence, and acceptance boundaries.
4. Classify work as read-only, disjoint authorized write, or overlapping or ordered write.
5. Build the delegation tree and dependency DAG under depth two and concurrency four.
6. Execute child tasks using bounded structured return contracts.
7. Classify non-success as retry, supplement, serialize, or escalate.
8. Let the stage owner synthesize evidence, integrate writes, resolve conflicts, and run stage-wide acceptance.
9. Hand only validated stage outputs to Orchestrator for the existing cross-stage gates and audit loops.
10. Accept the capability only when the proxy-metric scenario suite passes without weakening existing delivery gates.

## Residual Coordination

No unresolved business decision remains. Token-level reduction measurement is deliberately deferred until trustworthy runtime telemetry exists; this is a future measurement enhancement, not a blocker to the accepted phase-one delegation behavior.
